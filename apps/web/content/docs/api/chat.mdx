Chat SDK renderer. Turn JSON specs into [Chat SDK](https://chat-sdk.dev) cards, which each adapter posts in its native format: Block Kit on Slack, Adaptive Cards on Teams, and the card format of the other platforms.

## Install

```bash
npm install @json-render/core @json-render/chat chat zod
```

See the [Chat SDK example](https://github.com/vercel-labs/json-render/tree/main/examples/chat-sdk) for a playground that previews generated messages as Slack renders them.

## schema

The chat element schema for specs. Use with `defineCatalog` from core.

```typescript
import { defineCatalog } from "@json-render/core";
import { schema, standardComponentDefinitions } from "@json-render/chat";

const catalog = defineCatalog(schema, {
  components: standardComponentDefinitions,
});
```

The root element is a `Card`. Every component maps to a Chat SDK card element.

## streamCard

Stream a model's spec into a chat message. `streamCard` posts the card once its root element exists, edits the message as elements arrive, and finishes with a validated card.

```typescript
import { streamCard } from "@json-render/chat";
import { streamText } from "ai";

chat.onNewMention(async (thread, message) => {
  const result = streamText({
    model: "anthropic/claude-haiku-4.5",
    system: catalog.prompt(),
    prompt: message.text,
  });
  await streamCard(thread, result.textStream);
});
```

The target is any object with Chat SDK's `post(card)` method that returns a message with `edit(card)`, such as a `Thread` or a `Channel`.

If the final spec is invalid, `streamCard` throws `CardSpecError` after the partial message is visible, so you can retry or edit the message.

## toCard

Convert a complete spec to a `CardElement`. Post the result with `thread.post(card)`.

```typescript
import { toCard } from "@json-render/chat";

await thread.post(toCard(spec));
```

`toPartialCard(spec)` returns a best-effort card for a spec that is still streaming. It keeps the elements whose props validate and returns `null` until the root `Card` exists.

## State and repeat

Specs can read from `spec.state`. `toCard` resolves `$state`, `$item`, `$index`, and `$template` expressions, drops elements whose `visible` condition is false, and renders the children of an element with `repeat` once per item. A `Table` with `repeat` uses its rows as a template, with one copy per item. A `Table` whose `rows` resolve to objects matches each header to the key with the same name.

A `Fields`, `Actions`, or `Section` left without children, for example after a `repeat` over an empty array, is omitted, since platforms reject empty groups. A posted message has no inputs, so `$bindState` and `$bindItem` have no effect.

Expansion stops at `maxElements`, which defaults to 1000 elements and table rows, so nested repeats over state cannot grow without bound. `toCard` throws `CardSpecError` when a spec goes past it, and `toPartialCard` keeps what was expanded so far.

## Validation and limits

`toCard` validates the props of every element against its component schema and checks the structure of the spec, for example that a component without slots has no children and that the root `Card` has a title, an image, or a child. It throws `CardSpecError`, whose `issues` array has one readable entry per problem. Send the issues back to the model to get a corrected spec.

```typescript
import { CardSpecError, toCard } from "@json-render/chat";

try {
  await thread.post(toCard(spec, { limits: { tables: 1, charts: 2 } }));
} catch (error) {
  if (error instanceof CardSpecError) console.log(error.issues);
}
```

Platforms cap what a message can hold, and Chat SDK adapters degrade content past those caps. For example, the Slack adapter turns a second table into a code block. Pass `limits` to reject the spec instead.

## Native Slack Block Kit

Use `slackSchema`, `slackComponentDefinitions`, and `toSlackBlocks` for Slack-specific content. The native catalog adds message blocks that the portable card model cannot express: native cards and carousels, titled containers, multi-column layouts, context actions, plans, and task cards. It also exposes native versions of the existing message blocks, including data tables and data visualizations. See the [Slack Block Kit reference](https://docs.slack.dev/reference/block-kit/blocks/) for their payloads.

```typescript
import { defineCatalog, type Spec } from "@json-render/core";
import { slackSchema, slackComponentDefinitions, toSlackBlocks } from "@json-render/chat";

const catalog = defineCatalog(slackSchema, {
  components: slackComponentDefinitions,
});

const spec: Spec = {
  root: "message",
  elements: {
    message: { type: "SlackMessage", props: {}, children: ["status"] },
    status: {
      type: "SlackSection",
      props: {
        text: { type: "plain_text", text: "Deployment complete" },
      },
      children: [],
    },
  },
};

const blocks = toSlackBlocks(spec);
```

Pass `catalog.prompt()` to your model to generate native specs. With an existing Slack adapter, post the blocks through its Web API client:

```typescript
await slack.webClient.chat.postMessage({
  channel: "C123",
  text: "Deployment complete",
  blocks,
});
```

The root is `SlackMessage`. Native block names use a `Slack` prefix: `SlackActions`, `SlackCard`, `SlackCarousel`, `SlackContainer`, `SlackContextActions`, `SlackContext`, `SlackDataTable`, `SlackDataVisualization`, `SlackDivider`, `SlackHeader`, `SlackImage`, `SlackLayout`, `SlackPlan`, `SlackSection`, `SlackTable`, and `SlackTaskCard`.

Each block is a leaf with `children: []`. Put nested elements and composition objects directly in `props`, using Slack's field names and nested `type` values. Buttons, select and multi-select menus, pickers, feedback controls, workflow buttons, and composition objects retain their native payloads. Rich text can still appear inside native payloads, such as task details and table cells. Unknown native fields are preserved. The component supplies the outer block's `type`; omit it from `props`.

Use `SlackGroup` to group blocks or repeat children over state. `$state`, `$item`, `$index`, `$template`, `visible`, and group `repeat` resolve before conversion. `maxElements` defaults to 1000 expanded spec elements. `maxBlocks` defaults to 50 top-level blocks. These budgets do not count native objects nested inside props; Slack enforces their limits.

`toSlackBlocks` throws `CardSpecError` for invalid block props, missing elements, cycles, invalid nesting, or an exceeded budget. Nested native objects are retained as JSON; Slack validates their component-specific rules, surface eligibility, and aggregate limits. Each source element must have a single child reference; use `SlackGroup` to repeat blocks. Native blocks go directly to Slack's Web API and cannot be passed to `thread.post()` or `streamCard()`.

The message catalog intentionally omits `alert`, `file`, and `input` blocks: [alerts are modal-only](https://docs.slack.dev/reference/block-kit/blocks/alert-block/), files require Slack's remote-files API, and input blocks belong to modal/Home views. Dedicated `markdown`, `rich_text`, and `video` components are also outside this catalog's scope.
